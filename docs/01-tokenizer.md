# 01 · 分词：为什么模型第一个坎是"切词"

> 对应模块：站点左侧「① 分词」

## 一句话

模型不认识字符，只认识整数。分词器负责把任意文本切成一个个**子词单元（subword）**，再查表换成 id。**切得好不好，直接决定了模型贵不贵、中文流不流畅、数字算不算得对。**

## 为什么不能直接按字切，也不能直接按词切

先排除两个极端：

**按字切**（中文一字一 token）：词表极小（几千就够），但序列变得很长。注意力是 O(n²) 的，序列翻倍意味着计算量翻四倍。而且"模""型"两个字分开，模型得自己学会它们总是一起出现——浪费容量。

**按词切**（用空格和词典切英文）：序列是短了，但词表会爆炸（英文光动词变形就没完），更致命的是**未登录词（OOV）**问题：遇到训练时没见过的词，模型直接傻掉，只能给个 `<UNK>`。

子词（subword）就是这两者的折中：**高频词保持完整，低频词拆成有意义的碎片**。于是：

- 词表大小可控（GPT-2 约 5 万，LLaMA 3 是 12.8 万）
- 任意新词都能被拆成已知碎片的组合，不存在 OOV
- 碎片往往还带语义（`un-`、`-ing`、`-tion`），等于免费送了模型一些语言知识

## BPE 在干什么

BPE（Byte Pair Encoding）的思路朴素到令人意外，就四步循环：

```
1. 预分词：把文本切成互不跨越的单元
2. 初始化：每个单元拆成单个字符
3. 统计：找出语料里出现次数最多的相邻符号对 (a, b)
4. 合并：把所有 (a, b) 粘成新符号 ab，记进合并表，回到第 3 步
```

重复 N 次，就得到一个**带优先级的合并表**。编码新文本时，按优先级从高到低把字符依次粘回去。

关键在于第 1 步的"预分词单元"——**BPE 只在单元内部合并，绝不跨单元**。所以：

- 连续的汉字是一个单元 → 中文的合并机会被限制在连续汉字串内部
- 连续的英文字母数字是一个单元
- 每个标点各自独立

这就是为什么**中文几乎学不出多字词**。在真实的大词表模型里，常见中文词确实会被学进去（因为语料够大），但代价是词表里塞了大量中文词条，挤占其他语言的额度；而在小词表模型里，中文基本就是一字一 token。

## 一个可以直接验算的例子

英文语料里 `the` 出现了 50 次、`th` 出现 80 次。第一轮统计，`th` 的频次最高 → 合并成 `th`；下一轮 `the`（= `th` + `e`）的频次上来 → 合并成 `the`。最终 `the` 是一个 token。

中文语料里"模型"出现了 30 次，但"型"单独出现 100 次、"模"单独出现 90 次。如果它们处在不同单元里，这对永远统计不到一起——**它能不能成为一个 token，取决于预分词怎么切，以及它所处单元的频次。**

## 为什么中文更"费" token

这是很多人踩过的坑，一层层拆开看：

1. **信息密度差异**：同样一段意思，中文字符数远少于英文单词数，看起来中文更省。
2. **但 tokenizer 不是按"意思"切的，是按"语料频次"切的**。英文的高频组合被充分合并，`information` 可能只占 2 个 token；中文"信息"要么是两个 token，要么得在词表里专门占一个位置。
3. **结果**：真实场景里，同一段内容的中文 token 数经常是英文的 1.5~2 倍。

后果很实际：

- **API 成本**：按 token 计费，中文更贵
- **上下文占用**：同样 128K 窗口，中文装的内容更少
- **生成速度**：按 token 生成，中文输出更慢（每个字都得生成一次）

在站点的分词模块里，你可以直接输入同一段内容的中英文版本，对比"token 数"和"平均 token 长度"两个数字，这个差距会非常直观。

## 数字被切开这件事

还有一个高频坑：GPT-2 时代的 BPE 会把 `1234` 切成 `12` `34` 或者 `1` `234`，取决于语料。这直接导致早期 GPT 做算术很差——模型看到的是被随机切开的数字碎片，哪位数在哪儿全乱了。

LLaMA 3 之后的主流做法改成了**按位切数字**（`1234` → `1` `2` `3` `4`），算术能力明显改善。所以如果你在做涉及数字的任务，分词方式本身就是个需要检查的变量。

在站点里输入带数字的句子（比如 `GPT-4 有 1.8T 参数，上下文 128K token。`），观察数字被切成了几块。

## 压缩率：一个实用的健康指标

站点里给的"平均 token 长度"其实就是压缩率。它有一个很实用的用途：**评估某个 tokenizer 在你的领域文本上够不够用**。

做法：拿你业务里的真实语料跑一遍，看平均每个 token 覆盖多少字符。

- 英文 4 字符/token 左右是正常水平
- 中文 1~1.5 字符/token 是常见的
- 如果你的领域文本（比如医学术语、代码、化学式）明显低于基线，说明这个 tokenizer 在你的场景里效率很差，成本会比预期高不少

## 常见误解

**"token 就是词"** —— 不是。token 是统计产物，可能是词、词根、单字，甚至标点或空格。

**"同一个词永远切成同样的 token"** —— 不一定。BPE 的合并是在预分词单元内部做的，"hello" 在句首（带前导空格）和句中可能不同；而且很多 tokenizer 会给前导空格单独编码，所以 `hello` 和 ` hello` 是两个不同的 token。

**"词表越大越好"** —— 不是。词表大 → 序列短、计算省，但嵌入矩阵和最后的 unembedding 层变大，参数量与显存上升，且低频 token 学不到好的表示。这是个明确的权衡点。

## 在站点上怎么玩

1. 输入中英混排的句子，对比两类 token 的切分粒度
2. 拖动"合并次数"从 0 到 400，看 token 数怎么下降、词表怎么变大
3. 打开"合并过程动画"，看一个单元是怎么被一步步粘起来的
4. 换成自定义语料（比如贴一段你的专业领域文本），看学出来的合并规则会变成什么样
