# 07 · MoE 稀疏专家：为什么专家会饿死，以及两条治法为什么不一样

> 对应模块：站点左侧「⑦ 稀疏专家 MoE」

## 一句话

MoE 用「总参数很大、单 token 激活很小」换来了便宜的算力，代价是**路由器的负载天然会歪**；治它的两条路子（aux loss 梯度 / 负载反馈偏置）看起来在做同一件事，实际上差别巨大——因为前者对"死专家"的梯度**精确等于零**。

## 参数量账：先搞清 MoE 到底省了什么

设稠密部分（词表嵌入 + 每层注意力 + LayerNorm）为 `dense`，单个专家的 FFN 参数为 `E`：

```
total  = dense + (nExperts + nShared) · E · nLayers
active = dense + (topK     + nShared) · E · nLayers
```

**显存按 `total` 算，算力按 `active` 算。** 这两个数字差一个数量级，是 MoE 全部商业价值的来源。

站点里可以直接核对两篇官方数字（误差 5% 以内）：

| 模型 | 配置 | 官方总/激活 | 站点算出 |
| --- | --- | --- | --- |
| Mixtral 8x7B | d=4096, L=32, FFN=14336, 8 选 2 | 46.7B / 12.9B | 47.38B / 13.55B |
| Qwen3-30B-A3B | d=2048, L=48, FFN=768, 128 选 8 | 30.5B / 3.3B | 30.11B / 2.93B |

注意 Qwen3 的专家**特别细**（FFN 只有 768 维，而稠密模型同规模通常是 4 倍 d），专家越多越细，路由的组合空间越大，但负载均衡也越难做——这两件事是绑在一起的。

## 路由是什么

就是一次小型的注意力：

```
p(i,e) = softmax_e( cos(x_i, router_e) / T + b_e )
assign_i = TopK_e p(i,e)
y_i = Σ_{e ∈ assign_i} w(i,e) · Expert_e(x_i)      w = 在入选专家上重新归一化的 gate
```

`router_e` 是每个专家的路由向量（真实 MoE 里就是 router 线性层的第 e 行），`b_e` 是 logit 偏置。**注意这两组参数是分开的**：真实 MoE 里 router 是一个独立的小线性层，专家权重是另一套 FFN 参数。把两者混成一组，均衡力就会和专精力直接对撞，负载曲线会变成抖的、不可复现的——这是本站早期版本踩过的坑。

## 负载为什么会歪：三层原因

### 第一层：数据本来就歪（跟路由器无关）

真实语料的话题频率接近 Zipf：第 t 个话题的占比 ∝ `1/t`。站点用 48 个长尾话题 + 256 个 token，最热的话题就占了 **22%**，前 5 个话题占了一半以上。

**这一层是数据的先验，路由器学得再好也改不掉。** 想验证这一点：把 `均衡方式` 设为「不治」，你会看到倾斜 2.03 倍、但**一个死专家都没有**——因为话题数（48）远多于专家数（8），每个专家都有活干。

### 第二层：路由会自我强化

专精更新是 k-means 式的质心更新：

```
router_e ← router_e + lr · w · ( x_i − cos(x_i, router_e) · router_e )
                                        └────────── 切向分量 ──────────┘
```

被某个主题的 token 选得越多，`router_e` 就被拉得越靠近那个主题，于是更容易被继续选中。分工就是这么自己长出来的——热力图按主题排序后是块对角的，**没有人告诉过它哪个专家该管哪个话题**。

### 第三层：专家数 > 有效簇数 ⇒ 结构性死专家

把 `潜在主题数` 拖到 3，专家还是 8 个，立刻出现 **3 个死专家、倾斜 3.56 倍**。

这时候问题变了性质：不是"分配不均"，而是**根本没有那么多活给 8 个专家干**。你会看到热门专家在几个位置之间轮转（谁被顶上去谁就吃满流量），而死专家永远是 0。

**均衡力在这种情况下的作用是有限的**：它能让死专家的偏置被顶高、重新上岗，但它创造不出不存在的分工。这正是真实里"专家数远大于数据多样性时，大量专家退化"的成因。

## 两条治法，作用在同一个参数上

现代 MoE 都给每个专家配一个 logit 偏置 `b_e`，均衡力**只改这个标量**。区别在于"用什么信号"。

### 路线 A：aux loss 的解析梯度（Switch Transformer, 2021）

辅助损失是

```
L = n_E · Σ_e f_e · P_e        f_e = 分给 e 的 token 占比，P_e = 平均 gate 概率
```

完美均衡时下界 `L = 1`（站点里的 aux loss 读数可以直接对着这个下界看）。

按 Switch 的做法把 `f_e` 当常数（stop-gradient），对偏置求导：

```
∂L/∂b_e = n_E · f_e · (1/n) Σ_i p_i,e (1 − p_i,e)
```

**盯住 `f_e`。死专家的 `f_e = 0`，所以 ∂L/∂b_e 精确等于 0。**

站点里有一张专门的柱状图给这条结论作证：切到「⑥ 专家多于簇」场景，左边是负载、右边是这个梯度，死专家那一格打印出来就是 `0.0000`。这不是"梯度很小"，是"梯度就是零"——aux loss 对死专家**没有任何直接作用力**。

后果有两个，都能在站点上亲眼看到：

1. **曲线是抖的、非单调的。** 站点实测（强度 → 倾斜）：`0 → 2.03`、`0.5 → 1.69`、`1 → 1.16`、`2 → 1.22`、`4 → 1.78`、`8 → 1.19`、`16 → 1.81`。1 最好，4 和 16 反而更差。
2. **开过头会自己造出新死专家。** 强度 4 的时候偏置被推到 `|b| = 8.85`，硬生生把 8 个专家里的一个打死（dead=1），平均专精纯度从 0.545 掉到 0.470。

根因在于这个梯度**在最优处不归零**：`f_e` 被当作常数，损失函数并不知道"已经均衡了"，于是它一路推下去，把路由向量好不容易学到的分工冲掉。

### 路线 B：负载反馈偏置（DeepSeek-V3, 2024）

不用梯度，直接看实测负载偏差做负反馈：

```
dev_e = load_e / mean_load − 1
b_e  ← b_e − gain · dev_e / n_E
```

- 专家太忙 → `dev_e > 0` → 偏置往下调，少分点
- 专家空闲 → `dev_e < 0` → 偏置往上调，多分点
- **死专家 → `dev_e = −1`（最负）→ 偏置被顶到最高，自动重新上岗**

这是一个纯粹的负反馈回路：**负载一均衡，偏差自动归零，它自己就停手了。**

站点实测（同一个横轴，同一组配置）：

| 强度 | 0 | 0.5 | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- | --- | --- |
| aux 倾斜 | 2.03 | 1.69 | **1.16** | 1.22 | 1.78 | 1.19 |
| 负载反馈倾斜 | 2.03 | 1.44 | 1.13 | **1.06** | 1.03 | 2.00 |
| aux 需要的 \|b\| | 0 | 1.10 | 2.21 | 4.41 | 8.85 | 17.5 |
| 反馈需要的 \|b\| | 0 | 0.20 | 0.25 | **0.30** | 0.25 | 0.15 |

两个数字最值得记：

- **负载反馈只需要 `|b| ≈ 0.30`，aux 要 `2.2` 才勉强相当。** 偏置的量纲是 logit（`cos/T`，T=0.35 时量级约 3），所以 0.30 是"微调牌子"，2.2 是"把牌子掀了"。
- **aux 把偏置推得越大，分工被破坏得越厉害**：强度 4 时精度纯度从 0.545 掉到 0.470，同时出现死专家。

这就是 DeepSeek-V3 技术报告里说 aux loss "会损害模型质量、均衡效果受限于梯度信号"，从而改用偏置反馈的原因。**它不是把 aux 调小了，而是换了信号类型。**

## 公平起见：负载反馈也会过冲

强度开到 8，反馈也会过冲：倾斜反弹到 2.00、出现 1 个死专家。原因是增益太大时它对瞬时负载波动反应过度，偏置来回甩。

所以正确的结论不是"B 比 A 好"，而是：

> **用负载本身当信号，比用损失梯度当信号更贴合"我想让负载相等"这个目标**——因为前者的误差定义和目标定义是同一个，后者只是在优化一个代理损失。但在两种路线里，"信号强度"都需要调，都要防过冲。

## 硬限容量：第三条路，以及它的真实代价

`容量因子` 是另一套机制：给每个专家一个配额 `cap = ceil(n·topK/n_E · factor)`，超出配额的 token 直接**丢弃**。

- `factor = 1.25`：倾斜立刻从 2.03 压到 1.38，零死专家
- **代价是 24 个 token 被完全丢弃**（还有 24 个少拿到专家）

这不是"少算一点"那么简单：被丢的 token 在这一层的**残差通路里什么都不加**——它的表示原地跳过这个 Block。而且丢的总是热门话题的 token（因为它们挤在被限流的那几个专家上），**受害的是长尾里最重要的那部分信息**。

这也解释了为什么现代大模型（DeepSeek-V3、Qwen3）都倾向于"偏置反馈 + 温和容量"的组合，而不是硬限容量。

## 常见误解

**"MoE 的专家会自己分化成可解释的语义专家"** —— 站点里热力图确实呈块对角，但那是**在这个玩具设定下**（话题是正交的高斯簇）。真实 MoE 的专家分工要模糊得多，而且随层数变化：浅层偏语法/位置，深层才靠近语义。

**"加了 aux loss 就不会有死专家了"** —— 恰恰相反，站点实测强度 4 时 aux 会**造出**死专家。原因是 `f_e = 0` 时梯度为零，aux 管不到死专家；而它同时又在破坏活专家的分工。

**"top-k 越大越好"** —— k 从 1 到 2，倾斜从 2.03 降到 1.44；但平均专精纯度从 0.545 掉到 0.426。**专家越来越不"专"，越来越像稠密模型**——本质上是用稀疏性换平均性。Mixtral 用 8 选 2、Qwen3 用 128 选 8，都是在"细粒度"这条路上找平衡。

**"负载均衡只是个训练技巧，不影响推理"** —— 影响很大。负载不均意味着某些专家的权重被反复读写、某些几乎不碰，这直接决定推理时的 expert-parallel 通信量和显存热点，是 MoE 推理引擎最核心的调度问题。

## 在站点上怎么玩

1. 先点「① 不治：负载倾斜」，看热力图的块对角 + 负载柱状图的落差，明白**倾斜来自数据本身**
2. 点「⑥ 专家多于簇」，然后看「死专家的 aux 梯度精确等于 0」那张图——右边柱状图里有几根是 `0.0000`
3. 把 `均衡方式` 依次切到 `aux 梯度` 和 `负载反馈`，强度都设 2，对比两张卡里「当前配置」的倾斜和 `|b|`
4. 点「④ aux 开过头」，看 `死专家数` 和 `平均专精纯度` 一起变差
5. 回到「两种流派的曲线形状完全不同」那张图，沿着横轴从 0 拖到 16，注意紫线（aux）掉头、青线（负载反馈）单调
6. 把 `top-k` 从 1 拖到 2 再到 4，看专精纯度怎么一路掉下去
